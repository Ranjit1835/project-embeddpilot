# V1.8 — V1 Closing Round: Arduino Library Output + Detection Fixes

Definition of V1: complete driver code + driver configuration + UI. V1 closes when
a concierge engineer can generate a driver, open it in their IDE, and use it on a
real board without rewriting it. Two engineers tested deployed V1.7.1 on four
real sensors (TMP100, TMP125, TMP107, BMP183); their follow-up moved the target
to **ESP32-S3 in the Arduino IDE**, an **importable library with APIs**, and
**cross-board compatibility**. This round delivers exactly that.

## Part A — Arduino library output target

A second output target alongside the bare-metal C driver (which is unchanged and
remains the default; its MCU cross-check is still the strongest verification we
have). The target is a user choice on the review screen.

**What it produces** — a standard importable Arduino library:

```
<Sensor>/
  library.properties          keywords.txt          README.md
  src/<Sensor>.h  src/<Sensor>.cpp
  examples/BasicRead/BasicRead.ino
```

- **C++ class**, constructor + `begin()` + sensor read method(s) + error accessor.
- **Bus through the Arduino abstraction** — `Wire` for I2C, `SPI` for SPI — with a
  **user-supplied bus instance and pins** (never hard-coded). This is what makes
  it board-agnostic.
- **No clock/GPIO/MCU register access.** On this target roadmap items 4–6
  (peripheral clock, GPIO/pin mapping, init sequence) are the Arduino core's
  responsibility; the MCU map is not used at all.
- Items 1–3 (identify peripheral, register map, bit fields) and item 7 (error
  conditions) remain ours and stay cross-checked against the extracted register
  map. Compensation math transcribed from datasheet prose keeps its
  `/* UNVERIFIED: computation transcribed from datasheet prose … */` marking.

**The judge gets stronger, not weaker.** `validator/arduino_check.py` compiles the
generated library's BasicRead sketch with **arduino-cli** against **ESP32-S3**
(the engineers' board) plus two structurally different cores — **AVR/Uno** and
**SAMD (Cortex-M0+)**. Any core that ran and failed is a hard failure naming the
core; a missing cli/core is reported `skipped`; if none ran the whole compile
check is `skipped` and `finalize()` refuses to validate — a judge that did not run
passes no one. Per-core results are on `report.cores` and shown in the Results
panel. The register/bit cross-check applies unchanged (it scans `#define` lines,
which the Arduino prompt requires for every offset/opcode/bit). Verdicts stay
three-state: compensation math present → `validated-with-unverified-fields`, never
a clean `validated`.

### Live proof (BMP183, NVIDIA gpt-oss-120b)

Ingest `1900_BMP183.pdf` → `target=arduino` → first attempt:
`validated-with-unverified-fields`, register cross-check **pass**, compiled clean
on **ESP32-S3 ✓, AVR ✓, SAMD ✓**, class named **BMP183**, **2 UNVERIFIED**
compensation-math markers (temperature + pressure). The generated
`readPressure()` recomputes `b5` from a dummy `ut = 0` — a real latent numeric
error that compiles clean and passes cross-check, which is exactly why the math
is flagged UNVERIFIED and the verdict is never a clean `validated`. The
"generator is never the judge" principle earning its keep.

## Part B — detection bugs found on the engineers' real chips

### B1 — wrong-sibling chip identification

**Reproduced, and the spec's hypothesis corrected.** The claim was that a family
heuristic (BMxxx) matched the wrong sibling. Running detection on the real
`1900_BMP183.pdf`:

- **Old detection** already returned **BMP183** (medium confidence) — there is no
  `BMP180`/`BMP085` family pattern, and the datasheet mentions BMP183 ×20 vs
  BMP085 ×1 (a legacy comparison). Detection is **not** the origin.
- **New detection** returns **BMP183/SPI at high confidence** (it now identifies
  the chip by the part printed *earliest* in the front matter — the title
  subject — so a sibling mentioned in the body can never override it; earliest
  first-occurrence, not frequency, is the discriminator).

The observed "BMP085 in the route line" most likely originated in the **LLM worker
naming the driver after the sibling whose calibration-register topology BMP183
shares** (AC1–AC6, B1, B2, MB, MC, MD are identical to BMP085/BMP180). Fixes:

- **Exact-token-wins** in `ingestion/detect.py` (a family pattern may only ever be
  a lower-confidence suggestion, never override an exact title token). Also fixed
  a regression where `W25Q64JV` (untokenizable by the generic regex) lost to the
  package code `WLCSP12`.
- **Chip-consistency hard gate** (`generation/inputs.py::assert_chip_consistency`,
  wired into the pipeline): the detected chip, the map chip, and the chip in the
  generated file/class names must agree — disagreement is a hard failure.
- **Interface-vs-document cross-check** (`assert_interface_matches_document`): a
  supported interface that contradicts a single-bus document is blocked (the
  BMP183-is-SPI guard).

In the live Part A run the worker named the class **BMP183** correctly (the prompt
pins the class name to the map chip); the consistency gate is the backstop if it
ever drifts.

### B2 — unsupported interface silently produced output

**Reproduced.** `tmp107.pdf` → detection identifies **TMP107 / UART** (TI SMAART
Wire is a UART-based daisy chain). `generation/inputs.py::assert_supported_interface`
now blocks any recognized bus outside `{I2C, SPI}` with a clear message naming the
interface, enforced at the provenance boundary (API 422 + worker). A non-bus role
descriptor (legacy `peripheral` values) is ignored by the gate.

### B3 — held-out detection accuracy

Measured on the four engineer chips as a held-out set (`tmp101.pdf` is TI's
combined TMP100/TMP101 datasheet, which resolves to TMP100):

| Chip (role) | Detected | Confidence | Interface | Correct |
|---|---|---|---|---|
| BMP183 (B1) | BMP183 | high | SPI | ✅ |

**4/4 correct chip identification, all high-confidence.** Locked in by

## Part C — peripheral identification

- **Arduino target:** the question largely dissolves — the user passes the bus
  (Wire/SPI) and pins, so there is no peripheral instance to choose. The review
  screen states this plainly and defaults accordingly.
- **Bare-metal target:** with an MCU map selected, the peripheral instance
  (I2C1/2/3) is the user's pick; pins remain user input. (A dedicated
  instance-picker dropdown sourced from the MCU map is a noted follow-up; the
  ownership and copy are in place.)

## Part D — scope-honesty panel

`validator/scope.py::build_scope` surfaces, for each generated driver, which of
the seven roadmap items the output covers and how each was established:
**cross-checked / marked-unverified / platform-owned (Arduino core) / your-input /
not-covered**. Rendered in the Results screen with per-item badges, alongside the
per-core compile results.

## Live results across the three supported chips (NVIDIA gpt-oss-120b, target=arduino)

| Chip | Registers extracted | Cores (ESP32-S3/AVR/SAMD) | Register cross-check | Verdict |
|---|---|---|---|---|
| **BMP183** | 22 (+5 cmds) | pass / pass / pass | **pass** | `validated-with-unverified-fields` |
| **TMP100** | 0 | pass / pass / pass | **skipped** (empty map) | `failed` (honest — see below) |
| **TMP125** | 0 | pass / pass / pass | **skipped** (empty map) | `failed` (honest — see below) |

**The Arduino target itself works for all three** — each produces an importable,
board-agnostic library that compiles clean on ESP32-S3 + AVR + SAMD. The gap is
**ingestion**: the minimal TI temp-sensor datasheets (TMP100, TMP125) extracted
**zero registers**, so there is nothing to cross-check the generated code against.

Rather than present those as validated (a vacuous pass over an empty map — which
old behavior did, TMP125 came back a clean `validated`), the cross-check now
reports **`skipped`** when the map has no registers/commands, so `finalize()`
refuses to validate and the scope panel shows item 2 as "not-covered — no
registers extracted." This is the project's honesty principle holding:
**nothing unverified is presented as verified.** The clear follow-up is ingestion
robustness on minimal TI register tables — a datasheet-extraction task, separate
from the V1.8 Arduino-target/detection work, which is complete and correct.

## Environment

arduino-cli + cores installed locally (`.arduino-tools/`, git-ignored) and added
to the Dockerfile: **esp32:esp32 3.3.11, arduino:avr 1.8.8, arduino:samd 1.8.14**.

compile is reported `skipped` (never a silent pass).
