# V1.9 Build Report — Minimal Sensor Support

Follows the V1.9 spike (gate: proceed). Turns the four V1.8 "0 registers,
ungrounded" chips into **grounded** drivers — or an honest block — across three
vendors. Spike report: `V1.9_SPIKE_REPORT.md`.

## Item 1 — lookup-table false positive (highest-risk, done first)

A temperature→digital-output lookup table false-positived as a register index
(its multi-bit binary code column was read as hex "addresses" via `BINARY_RE`).
In TMP100/LM75B it parsed to 0 registers only by luck; elsewhere it could emit
**spurious** registers, poisoning the map the cross-check treats as ground truth.

Fix (`ingestion/registers.py::_is_value_code_lookup`): a table with a multi-bit
binary code column and no access column is never classified as registers, and
`parse_register_index`/`parse_headerless` refuse it too (defense-in-depth).
Confirmed on the real docs: TMP100 `register_index_headerless` **2→0**, LM75B
**1→0**; recall regressions (BMP180/BME280/W25Q64/ESP32/MCU) unchanged;
no-spurious-registers test included.

## Item 2 — pointer-register extraction + schema concept

Recognizes the dominant simple-I2C-sensor architecture, confirmed across **three
vendors** (TI TMP100, NXP LM75B, Microchip MCP9808):

- `parse_pointer_register_table`: binary pointer columns `[P1,P0,…]` / `[P2,P1,P0]`
  + a register-name column → registers whose offset IS the pointer value.
- `_promote_subheader`: recovers tables whose real column labels sit in the first
  body row (LM75B `P2|P1|P0|Register`) or under a merged super-header (MCP9808
  `Address (Hexadecimal)|Register Name`, direct hex addresses).
- Schema gains `access_pattern` (`pointer`|`direct`) — recorded explicitly so the
  worker is told the write-pointer-then-read access, not left to infer.

Grounded extraction: **TMP100** 4 regs (Temp@0x00 RO, Config@0x01, T_LOW@0x02,
T_HIGH@0x03), **LM75B** 4 regs (Temp/Config/T_HYST/T_OS), **MCP9808** 8 regs
(CONFIG@0x01 … Resolution@0x08).

## Item 3 — fixed-readout device shape (TMP125)

A register-less part is grounded by its readout parameters, not the compiler.

- `ingestion/readout.py`: extracts `{bit_width, value_msb, value_lsb, signed,
  lsb_weight, unit}` from a bit-position table (D15..D0 over T9..T0) + a value→code
  table + prose. **TMP125 → 16-bit word, value [14:5], signed two's-complement,
  0.25°C/LSB, high confidence.** Returns `None` (caller **blocks**) when it can't
  determine the params — never guesses.
- `schema.readout`; pipeline attaches it only for register-less devices.
- Worker: a fixed-readout Arduino path declaring the params as named `#define`s
  (`<CHIP>_WORD_BITS/VALUE_MSB/VALUE_LSB/SIGNED/LSB_WEIGHT`) and reading/slicing/
  sign-extending/scaling through them, board-agnostic SPI.
- `validator/readout_crosscheck.py`: verifies those `#define`s match the extracted
  params; a slice/sign/scale mismatch or a missing param is a **hard failure** —
  the required grounding rule. `finalize()` treats it as the grounding check when
  there is no register map.
- Required block condition: a register-less device with no readout is blocked.
- Scope panel renders **"no register map — FIXED READOUT device"**, distinct from a
  skipped check and from a failure.

## Deployed

V1.9 merged to `main` and deployed to Railway (`embeddpilot-api`); UI unchanged at
embeddpilot.vercel.app (the scope panel renders V1.9 data through the existing
generic renderer).

**Deployed V1.9 confirmed live.** The deployed backend's V1.9 *ingestion* is
verified on two chips: uploading the datasheet returns **TMP100 → 4 pointer
registers** and **LM75B → 4 pointer registers** (V1.8 returned 0 for both).

**Deployed end-to-end (upload → deployed ingest → deployed generate → deployed
validate on arduino-cli):**

| Chip | Deployed result |
|---|---|
| TMP100 | **validated-with-unverified-fields**, grounding **pass**, ESP32-S3/AVR/SAMD all pass ✅ |
| LM75B | **validated-with-unverified-fields**, grounding **pass**, 3 cores ✅ |
| MCP9808 | **validated-with-unverified-fields**, grounding **pass**, 3 cores ✅ |
| TMP125 | **validated**, readout cross-check **pass**, 3 cores ✅ |

**All four chips pass end-to-end on the deployed backend.** The three
pointer/direct register chips (TMP100, LM75B, MCP9808): deployed V1.9 ingest
(4/4/8 registers) → deployed generate → deployed validate with the **register**
cross-check passing, 3-core compile. TMP125 (fixed readout): deployed ingest
extracts the readout → deployed generate → the **readout** cross-check passes
(parameters matched) → clean `validated`, 3-core compile.

**Note on the TMP125 deployed run.** It took several tries to land purely because
of NVIDIA `gpt-oss-120b` latency this session (earlier deployed attempts variously
returned `unvalidated`, hit a transient poller timeout, or exhausted a ~13-min
poll with the job still running — the readout path needs a couple of ~3-min
attempts since the cross-check hard-rejects any wrong `#define` set, which is the
grounding working). It ultimately validated on the first attempt of a later run
once NVIDIA responded promptly. Provider is swappable via the deployed
`EMBEDDPILOT_PROVIDER` (Railway env) with no code change; it is set to `nvidia`
(NVIDIA's large context window is required for the V1.7 two-document MCU flow,
which 413s on Groq's window).
