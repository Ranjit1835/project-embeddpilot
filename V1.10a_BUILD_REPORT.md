## Honest framing (unchanged from the round brief)

- **This round does not fix BMP180/BMP183.** Their worked examples are trapped in
  figures (spike finding). No oracle is extracted for them; their compensation
  math stays `UNVERIFIED`. This is asserted by tests
  `test_bmp180_has_no_oracle_stays_unverified` / `_bmp183_`.
- **The BME280 check verifies TRANSCRIPTION FIDELITY, not mathematical
  correctness.** It compiles the datasheet's own reference function and diffs the
  generated math against it. That catches a copying error (the motivating bug
  class); it does not certify the datasheet's algorithm. The report/scope/notes
  say exactly this and never claim more.

## What was built

### 1. Host-execution harness — `validator/math_crosscheck.py`
The validator had only ever *compiled*; it now *runs* generated math.
- `find_host_runner()` prefers `gcc/cc/clang`, falls back to bundled TinyCC. No
  runner → check is `skipped` (a judge that did not run promotes no one — the
  same honest degradation as cppcheck). `tcc -run` is deliberately **not** used
  (it treats extra source files as program args, not sources) — both compilers
  compile every `.c` to one exe, then run it.
- Sandboxed: scratch-only temp dir, `RUN_TIMEOUT=20s` wall clock (a hanging
  generated program FAILS, it never hangs the run), no toolchain network use.

### 2. LM75B conversion-table path (`kind: "table"`)
- `ingestion/math_oracle.py::extract_conversion_table` pulls LM75B §7.5.2
  "Temperature Data Format" into vectors — **7 pairs including the 3 negative
  two's-complement rows** (−0.5/−25/−55 °C). Negatives are mandatory: they are
  where sign-handling bugs hide.
- The harness executes the generated `<chip>_raw_to_celsius` against every code;
  **exact** match required. A driver that drops the sign-extend is caught on the
  negative rows (`test_table_missing_sign_extend_is_caught`).

### 3. BME280 reference-code differential oracle (`kind: "reference_code"`)
- `extract_reference_code` locates `BME280_compensate_T_int32` in the text layer
  (§4.2.3, pp.25/50), normalises PDF typography (en-dash→minus, NBSP), and
  prepends the datasheet's own typedefs so it compiles standalone.
- The harness compiles the reference **independently** and diffs the generated
  `bme280_compensate_temperature` against it over an **8-point input spread incl.
  edge cases** (0, mid, max 20-bit `524287`, negative). Constants are
  harness-chosen test inputs (identical to both sides), never model-supplied
  answers. **Never** a string compare — numeric output only. A `>>2`-for-`>>3`
  transcription error is caught (`test_reference_transcription_error_is_caught`).

### 4. `math_crosscheck` integration + three states
- Wired in `validator/__main__.py` after the register/readout checks, feeding the
  same `ValidationReport`.
- Distinct states, never conflated: **`pass`** (executed, matched), **`fail`**
  (executed, diverged — hard failure), **`not_applicable`** (no oracle — the
  `UNVERIFIED` fallback stands, *not* a failure), **`skipped`** (no host
  compiler). Rendered distinctly in `validator/scope.py`.
- Provenance guard: an oracle whose `provenance` is not `detected`/`user` is a
  hard failure (`test_model_provenance_is_rejected`) — a model-supplied expected
  value would make the check worthless.
- Contamination guard unchanged: no `generation/` imports; the marker literals
  stay duplicated across the boundary.

### 5. Verdict-promotion rule — `validator/report.py::finalize`
- `scan_unverified_computations` now records the **enclosing function** of each
  marker; a passing math check records the **entry points it executed**
  (`verified_computation_entries`).
- `_remaining_computations()` discounts a marker **only** if its function was
  executed and matched. Promotion `validated-with-unverified-fields` → clean
  `validated` happens **only when every unverified item is covered**. Tested in
  both directions, including the erosion-prone case: a passing math check + a
  remaining unverified **bit field** must **not** promote
  (`test_promotion_denied_with_remaining_unverified_field`), and an **uncovered
  sibling computation** must not promote
  (`test_promotion_denied_when_a_computation_is_uncovered`).

### 6. Schema — `math_oracle` (approved addition)
Added to `schema/register-map.schema.json`: `{kind, entry, input/output_ctype,
tolerance, provenance∈{detected,user}, source_pages, [vectors] | [reference_*,
calibration, input_spread]}`. Attached by the ingestion pipeline; absent for
figure-only parts.

### 7. Worker contract
`generation/worker.py::_math_oracle_section` tells the worker (bare-metal C
target) to expose the math as a free function with the exact name/signature the
harness calls, still preceded by the `UNVERIFIED` marker (the executor clears it
only on a match).

## Live verification — DONE via Gemini free tier (2026-08-24)

Run end-to-end through the real LLM worker on the **bare-metal C** target, provider
`gemini/gemini-3.6-flash` (free tier; `EMBEDDPILOT_PROVIDER=gemini`), validator +
`math_crosscheck` executed locally with TinyCC:

| Chip | Verdict | math_crosscheck | Note |
|---|---|---|---|
| **LM75B** | `validated-with-unverified-fields` | **pass** | conversion executed vs the datasheet table, 7 vectors incl. 3 negatives, exact |
| **BME280** | **`validated`** (clean) | **pass** | differential vs `BME280_compensate_T_int32` over 8 inputs incl. edges; the **promotion rule fired live** (marker cleared, no remaining unverified items) |

The live run was a genuine shakedown and surfaced three defects the deterministic
tests could not — all fixed:
1. **Harness main-clash** (`validator/math_crosscheck.py`): the bare-metal target
   ships `<chip>_example.c` with its own `main()`, which clashed with the probe's
   `main` → compile failed → check wrongly `skipped`. The harness now excludes any
   source that defines its own `main` (`_without_own_main`).
2. **Table-oracle representation** (`ingestion/math_oracle.py`): vectors fed the
   bare N-bit code, but a correct driver reads the full register WORD with the code
   **left-justified** (LM75B 9-bit code in a 16-bit word). A correct Gemini driver
   looked wrong (a false negative). The extractor now left-justifies vectors into
   the read word (`word_bits`), and the worker contract says the entry point takes
   the assembled register word. This flipped LM75B to a true pass.
3. **JSON control chars** (`generation/provider.py`): models emit literal
   newlines/tabs inside JSON string values (raw code in `source_c`); strict
   `json.loads` rejected them, failing every large-driver response. `_parse_json`
   now uses `strict=False`.

Also found: `gemini-3.6-flash` is a *thinking* model — its reasoning tokens share
the output budget, so `GEMINI_MAX_TOKENS=8000` truncated the JSON; `24000` fixed
it (3.x flash supports a large output window).

## Remaining: deploy (optional; needs the deployed provider env)

The deterministic build is complete and fully tested locally. The final DoD
items — the real LLM worker following the new contract, verified end-to-end
through the deployed backend — require the session `NVIDIA_API_KEY` and a Railway
redeploy, which are provided per session. The Docker image already ships host
`gcc`, so `math_crosscheck` runs there with no image change. Run:

```
# local live (bare-metal C target):
EMBEDDPILOT_PROVIDER=nvidia NVIDIA_API_KEY=nvapi-... NVIDIA_MAX_TOKENS=12000 \
  python -m generation.pipeline  <lm75b map>  --target bare-metal
# deploy: railway up --service embeddpilot-api --ci   (gcc already in image)
```

Note: LM75B/BME280 live proofs should target **bare-metal C** — the math check
executes C free functions; the Arduino C++ library path reports `skipped` for the
math check (the conversion lives in a C++ method, out of scope this round).
