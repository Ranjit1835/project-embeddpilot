# EmbeddPilot V1.10a — Spike Report: Golden-Vector Verification of Compensation Math

**Type:** Feasibility spike (investigate → report → gate). No build.
**Date:** 2026-08-24
**Discipline honored:** diagnostic scripts ran from the scratchpad only and were removed; **no changes** to `validator/`, `ingestion/`, `generation/`, the canonical schema, or the UI. Any schema addition is *flagged for approval below*, not introduced.

---

## TL;DR — gate recommendation: **QUALIFIED PROCEED (pivot the mechanism)**

The hypothesis as written — *extract the datasheet's worked numeric example and use it as a golden vector* — **fails on the primary target and its closest sibling**, because their worked examples live inside **figures (images)**, not the text layer. Do **not** build "worked-example golden-vector extraction" as the primary mechanism.

But the spike found the *goal* (mechanically verifying comp/conversion math) **is** achievable for a meaningful subset via **different, text-extractable artifacts** the hypothesis didn't anticipate:

- **Conversion-table vectors** (LM75B): clean text table of `digital code → temperature` pairs, incl. negatives — a real golden vector for linear readout math.
- **Reference compensation code** (BME280): the datasheet's own integer `BME280_compensate_*` functions, verbatim in text — a **differential-testing oracle** stronger than a single vector.

**Recommendation:** proceed, but re-scoped to those two mechanisms; treat figure-trapped examples (BMP180/BMP183) as an explicit *stays-UNVERIFIED* case (OCR is a weak, later option). Details and ordered build requirements below.

The calibration table itself (Table 5, page 13: AC1…MD register addresses) *is* clean text — but that's register *addresses*, not the example's numeric *values or outputs*. The worked example — the thing that would be the golden vector — is 100% trapped in the figure. This is a WS1-class finding: with current tooling the honest output is `null`, not a guess.

## Item 2 — held-out survey: worked examples are **not** a portable convention

Per-document, from the text layer (pdfplumber, the production ingestion path):

| Datasheet | Worked numeric example? | Reference conversion code? | Form / extractability |
|---|---|---|---|
| **BMP180** (Bosch) | Present but **image-only** (Fig 4, p15) | "available on request", not in-doc | ❌ not extractable |
| **BMP183** (Bosch) | **Image-based** (Fig 4, p15); figure is *vector* so the text layer leaks **only the two raw inputs** `27898`/`23843` amid a jumble of C type keywords | not in-doc | ❌ incomplete — **calibration constants and all expected outputs (`2399`,`150`,`69964`,`408`,…) absent from text**; raw inputs alone can't form a vector |
| **BME280** (Bosch) | No single numeric vector, but **full integer reference functions** `BME280_compensate_T_int32` / `_P_int64` are **clean text** (p25, p49–50), incl. output-format anchors ("`5123` = 51.23 DegC", "`24674867`/256 = 963.862 hPa") | ✅ **yes, verbatim** | ✅ text-extractable → **differential oracle** |
| **MCP9808** (Microchip) | Conversion **Equation 5-1** + sample decode **code** as text (p25); no numeric input→output vector found | partial (equation + code) | ⚠️ equation/code text-extractable; no clean numeric vector |
| **LM75B** (TI) | **Yes** — §7.5.2 "Temperature Data Format" is a clean text table of 7 `°C ↔ binary ↔ hex` pairs incl. negatives (125°C=0FAh, 0.5°C=001h, −0.5°C=1FFh, −55°C=192h, …) | n/a (linear) | ✅ **text-extractable golden vector** |

**Conclusion for Item 2 — do not generalize from Bosch, and don't generalize the hypothesis either.** Numeric worked examples are neither common nor reliably text-extractable. What *is* reliably text-extractable is one of two *other* artifacts: a **conversion table** (linear parts) or **reference code** (complex compensation). The Bosch pressure sensors — the exact parts that motivated this round — are the **worst** case: their examples are figures.

## Item 3 — execution mechanism

The validator today **only compiles** (`arm-none-eabi-gcc` cross-compile, `arduino-cli`, `cppcheck`) — it **never runs a produced binary**. Verifying math requires *executing* it, which is **new capability**. Tooling status:

- **Host `gcc` is already in the Docker image** (`gcc libc6-dev` in `Dockerfile`) → native compile-and-run is feasible **in the cloud/deployed backend**.
- **Host `gcc` is absent locally** (Windows) → local runs would **skip**, exactly like `cppcheck` today (cloud is the stronger check — an established pattern here).

Two mechanisms considered:

**(A) Extract-the-function + host-harness (recommended first).** Pull the compensation/conversion function from the generated driver, compile it standalone with a tiny host `main` that injects the vector's constants + raw inputs, run, compare stdout to expected.
- *Pros:* smallest surface; mirrors the `readout_crosscheck` discipline (target named things, not arbitrary expressions).
- *Cons:* function extraction is fragile for stateful math — BME280 carries a `t_fine` **global** across T→P and needs the 64-bit path; the harness must reproduce that context.

**(B) Whole-driver + mock bus, host-run.** Compile the entire driver for host against a mock bus returning the vector's raw bytes; read the driver's output.
- *Pros:* exercises the real read→slice→scale→compensate path end to end.
- *Cons:* requires the driver to be host-runnable (callback stubs, host `main`), heavier; more moving parts.

**Contamination-guard implications (hard rules):**
- The vector/oracle **comes from the document, never the model** — LM75B table cells and BME280 reference code are datasheet-sourced; an LLM must never supply expected values.
- **The checker must not be the generator.** For the BME280 reference-code oracle, the harness compiles the **datasheet's** reference function *independently* and **diffs numeric outputs** across inputs — never a string-compare against the generated code, and never code the worker authored.
- The marker-string / oracle plumbing must stay duplicated literals across the generator/validator boundary (the existing `COMPUTATION_MARKER` ⇄ `COMPUTATION_UNVERIFIED_COMMENT` no-shared-import rule).

## Item 4 — legitimate tolerance

| Path | Arithmetic | Tolerance | Achievable? |
|---|---|---|---|
| BMP180 / BMP183 | integer fixed-point | **exact** (any deviation = real bug) | vector unreachable (figure) |
| **LM75B** | linear, 0.5°C LSB, two's-complement | **exact** | ✅ yes (table is text) |
| MCP9808 | fixed-point, 0.0625°C LSB, sign-handled | **exact** | vector not clean; equation only |
| **BME280 (int path)** | int32/int64 fixed-point, deterministic | **exact** vs the reference function's output | ✅ yes (reference code is text) |
| BME280 double / float variants | floating point | epsilon (e.g. 1e-2 on the doc's stated resolution) | only if float path chosen |

The important, honest point: **the integer paths (which is what these sensors actually use) demand exact equality** — no epsilon fudge. Exact match is achievable precisely where the ground truth is text (LM75B, BME280-int); it is *not* achievable where the ground truth is a figure (BMP180/BMP183).

## Item 5 — when no example exists (the common case)

Most parts have neither a numeric vector nor reference code. The fallback **must remain the current `/* UNVERIFIED */` marking** → `validated-with-unverified-fields`. Never present a weaker check as verification. Concretely, in priority order:

1. Text conversion table present → build a vector, verify **exactly** (LM75B).
2. Text reference code present → **differential-test** the generated math against it (BME280).
3. Example only in a figure → **stays UNVERIFIED.** OCR is a *possible later* path but is weak here: the hardest cells to OCR (negative two's-complement constants, superscripts, expected outputs) are exactly the ones we need, and confidence-gating would likely reject them. Do not ship OCR'd vectors without a high-confidence gate.
4. Nothing present → **stays UNVERIFIED** (status quo). Honest, unchanged.

## Gate recommendation (detail)

**Proceed to build — but pivot the mechanism, and scope it to what the evidence supports.** Do **not** build worked-example extraction (the primary target defeats it). Build, in order:

### Ordered build requirements (if approved)
1. **LM75B conversion-table vector path first** (lowest risk, fully text, exact). Proves the end-to-end machinery — extract table → build vector → execute generated conversion → exact compare — on the cleanest case.
2. **BME280 reference-code differential oracle** (higher value, still text, exact on the integer path). Compile the datasheet's reference function independently; diff outputs across a spread of inputs incl. edge cases.
3. **Host-execution harness** = mechanism (A): extract-function + host `main`, host `gcc`. Skips locally (like cppcheck), runs in Docker. This is the one genuinely new dependency on the validator.
4. **New check `math_crosscheck`** slotting alongside `register_crosscheck` / `readout_crosscheck` in `validator/__main__.py`, feeding the same `ValidationReport`. Same discipline as `readout_crosscheck`: verify the grounded thing, refuse to validate an ungrounded one only when a vector/oracle is *available* (its absence is not a failure — it's the UNVERIFIED fallback).
5. **Figure-trapped examples (BMP180/BMP183) explicitly out of scope** → they keep the `COMPUTATION_UNVERIFIED` marker. Note this in the scope panel.

### Verdict-promotion rule (answering the spec's explicit question)
A driver whose math **passes** `math_crosscheck` **may** be promoted from `validated-with-unverified-fields` → clean **`validated`** — **but only when the passing check covers *every* unverified item present.** Precisely:
- Promotion covers **exactly the compensation/conversion computation(s) the vector or oracle exercised.**
- Promotion does **not** cover: unverified **bit fields** (`unverified_fields`), MCU **init/sequence** markers (`SEQUENCE_MARKER`), AF numbers, or any computation the oracle did not exercise. If any of those remain, the verdict stays `validated-with-unverified-fields`.
- Mechanically: in `finalize()`, a computation whose marker is *matched by a passing math-check* no longer counts toward the `unverified_computations` downgrade; if that empties both unverified lists, the status rises to `validated`. (This is a `finalize()` change — flagged, not made.)

### What stays unverifiable (for the scope-honesty panel)
- Compensation/conversion math on **figure-only** parts (BMP180, BMP183) until/unless a gated OCR path exists.
- Any math with **no** in-document vector or reference code.
- Math the oracle can't reach (e.g. a float path with no stated reference).
- Correctness of **inputs the user supplies** (pins/AF) — out of scope for this check, as before.

### Schema additions — FLAGGED FOR APPROVAL (not introduced)
Mirroring how `commands` (WS1) and pointer-register (V1.9) were flagged:
- A **`math_oracle`** (or `golden_vectors`) concept on the register/sensor map: `{ kind: "table" | "reference_code", inputs, raw_values, expected_outputs, tolerance: "exact"|float, source_pages, provenance }`.
- Provenance must be `detected`/`user` (never model), consistent with V1.6 `assert_input_provenance`.

### Cost / timing
- **Extraction:** negligible — a few extra pages scanned; no LLM tokens.
- **Execution:** modest CPU per attempt (compile+run a tiny host program); new but small. Host `gcc` already in the image → no new Docker layer for BME280/LM75B. Local runs skip (documented degradation).
